# Lessons — XMage Nexus

Durable, hard-won lessons (one line each). Add one only when it is reusable;
the historical narrative lives in `git log`. Scoped docs: `AGENTS.md` (daily
ops), `docs/testing.md`, `web/AGENTS.md`, `Mage.Proxy/README.md`.

## Server & protocol

- JDK 17: both proxy and server need `--add-opens=java.base/java.io=ALL-UNNAMED` or jboss-serialization fails.
- `deckType` must match a real server config name (e.g. `Constructed - Modern`); client and server versions must match strictly (local: `config.xml` + `plugins/`).
- `createTable` requires the deck's `quitRatio` ≥ the user's (default 100); AI seats are filled **before** the human seat.
- "Any target" prompts include both players: use the opponent's UUID, not `targets[0]` (it can be yourself).
- `watchTable` only yields `WATCHGAME` once the table is `DUELING`, and the XMage client's `SessionImpl.watchTable` returns `true` regardless, so one sent right after `startMatch` can be silently dropped: re-send it every ~500 ms until `WATCHGAME` (a single retry 20 s later loses to fast AI-vs-AI games that already ended).
- Game events keep arriving ~1 min after the watcher closes; "broadcast to 0 connections" is normal for game events, a bug signal for lobby events.
- A killed proxy session (`kill -9`) leaves its socket on the server: new logins then fail with `SESSION CALLBACK EXCEPTION - Unable to create socket` until server+proxy restart.
- Test mode caps `maxGameThreads` (10); browser E2E leaves matches running — restart the server between heavy batches.
- Keep the demo AI deck stable (Islands + Mountains + 4 Bolts): 16 Bolts make AI-vs-AI matches end in 2-3 turns, hiding board interactions.
- macOS `/usr/bin/java` is a stub: resolve the real binary (Homebrew `openjdk@17` first); `scripts/lib.mjs` `javaBin()` does this.
- Generated usernames must be ≤14 chars (`maxUserNameLength`); login failures log the misleading `Can't receive server state before other data`.
- `TableView.games` is `Match.getGames()` order (oldest first) and keeps finished games: `watchGame` on one of those returns `false` (no `GameController`), so a spectator "follow" must only pick a game *after* the watched one (`findFollowGameId`).
- `tableRemove` returns `void` and silently ignores non-owners (`SessionImpl.removeTable(roomId, tableId)` is `true` whenever connected), so the proxy checks `getTable` + `isTableOwner` itself; and `createTable` + seat joins are not atomic: a failed join must `removeTable` the fresh table or every retry leaves a stray one in the lobby. The room's table list refreshes on a timer, so `getTables` right after `createTable` can still be empty.
- Rollback vote: every other in-game HUMAN seat must accept (proxy SIM seats count too, so `SimPlayer` auto-accepts rollback requests), one deny cancels it, there is no timeout, the game is not paused, and `turnsToRollback` is applied to the turn in which the **last** accept arrives (a "current turn" request from turn 3 accepted in turn 4 rolls back to turn 4). Individual accepts are not broadcast (only the deny and the final `Rolling back to start of turn N` reach the chat), so the web announces its own accept in chat (with a turn/time suffix: the server's chat anti-spam silently drops a user's identical consecutive line); the dialog title names the voter, not the requester (use `relatedUserName`). Verified by `scripts/verify-rollback-vote.mjs`.

## Proxy & sessions

- `connect` must be idempotent per `host|username` (browser reloads): restarting the session clears WS registries and triggers reconnect loops; test mode kicks duplicate connections from the same host.
- Every `SessionImpl` (web client, SIM, future bots) needs its own keep-alive ping or `UserManagerImpl` expires it (~4 min lease) and the game declares the seat lost/quit.
- Archidekt's `/api/decks/{id}/small/` now returns `cards: []`: import from the full `/api/decks/{id}/` (~350 KB) and drop cards in any category with `includedInDeck: false` (Maybeboard); `deckFormat` is numeric (3 = Commander). Fixture: `web/src/decks/__fixtures__/archidekt-deck-15000794.json`.
- The public proxy sits behind a TCP tunnel (playit): sockets die without a close frame (`1006`) or stay half-open for minutes, while the browser keeps them `OPEN` and every click goes nowhere. The web runs its own heartbeat (`net/Gateway.ts`: `ping` after 15 s idle, dropped and reconnected if nothing arrives within 10 s, also on focus/`online`), and the proxy answers `ping` on the WebSocket thread (`Gateway.pingRequestId`), never queued behind a slow command of the session, which would read as a dead socket.
- Never end a player's XMage session as a reaction to a timeout: `connectStop(false, false)` is `DisconnectedByUser` on the server (`Main` `removeListener`), which removes the player from **every table**, so the game counts as abandoned. `connectStop(false, true)` (keepMySessionActive) is no better in a proxy: the server keeps a zombie session whose callbacks block a server thread ~60 s each (`SESSION CALLBACK EXCEPTION - Unable to create socket`, even stalling other users' logins) and still expires it with table removal after 3 min. Keep the session alive while the web is away (`--graceSecs`, default 180 s); a proxy that dies without disconnecting is a lost connection to the server (tables kept, restored by `User.onReconnect` on the next login). The one safe use of `keepMySessionActive` is right before logging the same account in again (the proxy's relink after a lost server link, a SIM's reconnect): the new login disconnects the hidden session at once (`AnotherUserInstanceSilent`, tables kept).
- Server callbacks reach `MageClient.onCallback` out of order (the client `SessionImpl` hands batches over from several remoting threads): a reconnect's re-asked `GAME_SELECT` overtook its `START_GAME`/`GAME_INIT`. The callback `messageId` is one contiguous counter per server session, so the proxy re-sequences them (`CallbackSequencer`, gaps skipped after 400 ms).
- The reconnect restore (`START_GAME`, `GAME_INIT`, the re-asked prompt) arrives **during** `connectStart`, before the logging-in WebSocket is authorized; the proxy buffers what it broadcasts during a login and hands it to that connection right after the `connect` result.
- Java-WebSocket runs `onClose` on its selector thread while holding the connection's monitor: never synchronize on the `WebSocket` object, and never take a session-wide lock in `onOpen`/`onClose`/`attach` (a login holds it for up to a minute; the whole WebSocket server stalls for every user). With permessage-deflate the per-connection Deflater is not thread-safe, so sends are serialized on a private per-connection lock (`Gateway.send`).
- A re-attach (a second window, or the same window after a network blip) is announced with a `connected` event just like a fresh login: the web must not leave a game in progress on it, only reset its per-session event ordering. A login that opened a new XMage session (`connect` → `attached: false`) restarts the callback ids at 1: the web resets its ordering on that result too, and a `GAME_INIT` re-bases the order instead of only raising it (a stale high-water mark dropped every update of the restored game as older).
- `SessionImpl` calls `MageClient.disconnected` (lost lease → `connectReconnect`, and `connectStop`) while holding its own monitor, and `ProxyClient.connect()` holds the client's monitor while it waits in the synchronized `connectStart`: anything `disconnected` does must not take the client's monitor (the relink is started under a private lock and runs on its own thread). `disconnected` is also called by the proxy's own stops and failed logins; only an unexpected one starts a relink (`expectDisconnect`).
- The cached prompt for the re-attach replay must live until the player answers it: the server sends `GAME_UPDATE`s while a prompt is open (timers, other players), and clearing the prompt on any update replayed a board with no prompt, so the player saw "waiting for the opponent" on their own turn. Take it out **before** sending the answer (the next prompt can arrive while the call runs) and put it back if the server rejects the answer.
- Replaying only the latest state and prompt loses every other event of the gap (`SIDEBOARD`, a game 2 `START_GAME`, `GAME_OVER`, chat). The proxy numbers its frames per session (`seq`) and keeps a log a returning connection resumes from; a plain `GAME_UPDATE` replaces the older one of its game in the log, so a long absence costs one state per game, not every update.
- SIM usernames must never repeat across proxy processes: the server takes a login with a known name from the same host as a **reconnection** and hands the new bot the old bot's tables. The counter starts from the clock and above the names on the SIM roster.
- A closed tab and a dropped connection look the same to the proxy (the socket closes), but they need different waits: the web announces `leaving` on `pagehide` and the proxy then keeps the session 45 s instead of 180 s. `pagehide` also fires on a reload, which is harmless because the reload re-attaches within seconds; a phone put in the background normally fires only `visibilitychange` (no `pagehide`) and keeps the long wait.
- An automatic relink must never fight another login of the same account: the server kicks the older instance of a user (`Disconnecting another user instance`), and the kicked client sees the same lost link as a network drop. Two relinking clients kicked each other every ~2 s forever (seen when a login retry opened a second proxy session while the first login waited ~60 s on the server). The proxy holds the account while a login runs (a concurrent `connect` queues and attaches) and gives up when a session is lost again within 2 minutes of its relink.
- jboss' connection validator reports a lost link after a 3 s ping timeout, and a server that is sending callbacks to dead sessions (each blocks a thread until `Unable to create socket`, tens of seconds) misses it for healthy sessions too. Never log in again on that report alone: ask the server with the session itself first (`SessionProbe`, the server's `ping(sessionId)`, since `SessionImpl.ping()` swallows failures). A relink on a false alarm kicked the healthy session, left one more dead session and froze the game thread (`Game frozen in waitResponseOpen`).
- Diagnosing "the game froze" on the public proxy: `[activity]` does not log in-game answers (`sendPlayer*`, `ping`), but prompts are logged (`event >> GAME_SELECT (msgId=…)`) and the game log arrives as `CHATMESSAGE` on the game chat id, so a game that goes silent after a prompt until the player's `login_attach` + `joinGame` was waiting on that player's client. `ws_close code=1001` is a reload/navigation, `1006` a dropped connection; a burst of `updatePreferences` means Space pressed on a focused PhaseBar stop button.

- playit forwards public traffic to `127.0.0.1`, so on the host every tunnel visitor looks like localhost (`ip=127.x.y.z` in `[activity]`): "local only" must mean a port with no tunnel **plus** a LAN CIDR allowlist that rejects loopback (`ops/status/server.mjs` `clientAllowed`), never "allow 127.0.0.1".
- Parsing the proxy's journal: JUL writes the header (`sept 27, 2026 3:08:13 A. M. Class method`, with U+202F/U+00A0 inside `A. M.` on JDK 17 + es locale) and the `LEVEL: message` line as separate journal entries, and log4j lines from other threads can land between them; match with `\s` and only let a JUL level line consume the header.

## Web client

- Order views of the same game by the server `messageId` (monotonic per XMage session, `mage.server.Session`), not by turn/step: extra combats and main phases move the step backwards within a turn, and the turn/step guard froze the board for the rest of the turn (it also ranked `FIRST_COMBAT_DAMAGE`/`COMBAT_DAMAGE` below `DECLARE_BLOCKERS`). Only an earlier **turn** stays stale unless a rollback is armed. The order resets on every `connected` (a new session restarts the ids), and the first view after it is accepted (`gameEventOrder` in `state/gameUtils.ts`).
- Keyword badges on permanents come from keyword-ability lines only (`extractOwnedKeywords`): "can't be blocked except by creatures with flying or reach" or "create a token with vigilance" mention a keyword the object does not have. The same applies to `hasVigilance`, which decides whether an attacker is drawn tapped.
- The tap rotation lives in `transform`, so any hover/animation that also writes `transform` replaces it and the card straightens: board effects must use the independent `translate`/`scale` properties, which compose with it (guard: `web/e2e/tapped-rotation.spec.ts`).
- A mouse-clicked `<button>` keeps focus, so a global shortcut guarded by "ignore keys on native controls" dies after any toolbar click (Space stopped passing priority after clicking the log toggle): release mouse-focused game controls on Space instead (`mouseFocusedGameControl`), keep the guard only for keyboard focus, text entry, dialogs and menus (guard: `web/e2e/control.spec.ts`).
- Decorative duplicates of visible text (e.g. the cinematic end title) go in a `data-*` attribute rendered with `::before { content: attr(...) }`: a second text node with the same string makes `getByText` find multiple elements and breaks existing tests.
- Fixed-size layout boxes that crop content must use `overflow: clip`, not `hidden`: a `hidden` box is still a scroll container, so focusing a child that peeks past its edge (a clicked hand card) scrolls the whole board by up to ~100px and it never scrolls back (guard: `e2e/board-scroll.spec.ts`).
- `state/slices/*` must only import dependency-free modules: pulling a helper that reaches `board/*` (e.g. via `commanders.ts`) creates an import cycle and a TDZ crash at store init; keep catalogs (`appearance/playmats.ts`) separate from game-aware helpers (`playmatIdentity.ts`).
- Full-screen overlays opened from inside a board zone (resource bar, player zone) must `createPortal` to `document.body`: those zones set `position` + `z-index`, so the overlay's own `z-index` only competes inside that stacking context and the divider strip, pass button and hand paint over it (the ray/cross-zone viewer did, 2026-09-23).
- `CardView.originalPower`/`originalToughness` arrive as a serialised MageInt (`{ baseValue, modifiedBaseValue, boostedValue, cardValue }`), not the `string | null` the contract declares; read them through `board/ptTrend.ts` (`cardValue` = printed value, `baseValue` when it is `*`).
- `canPlayObjects` lists every untapped mana source (only `basicManaAbilities`), so "something is playable" must ignore mana-only entries (`game/smartStops.ts`).
- `canPlayObjects` can arrive **empty** during a mana-payment sub-loop that isn't a normal spell cast (e.g. a "pay {2} to attack" cost like Propaganda: verified live, 2026-09-23) even with untapped lands/Treasures on board; gating permanent clicks on `playableIds` then makes nothing clickable. The official client never gates on `isPlayable` (`CardPanel.mouseClicked` always forwards the UUID and lets the server accept/reject), so `useBoardPresenter.ts` forwards any permanent click during `feedback.mode === 'mana'` regardless of `playableIds` (`manaFeedbackActive`). This gap is **not universal** to every off-cast mana ask, though: an Echo payment resolving in upkeep (`fixtures/recorded/echo-upkeep.json`) gets `canPlayObjects` populated correctly — so far only the cost-to-attack sub-loop is confirmed empty. Don't assume a mechanic is broken just because it pays mana outside casting; check `canPlayObjects` in the live `GAME_PLAY_MANA` payload (`REC_DUMP_EVENTS=1` in `scripts/record.mjs`) before writing it off. The client-side fix covers both cases either way.
- Auto-pass must answer only the view that came with a `GAME_SELECT`, once: the real server sends a `GAME_UPDATE` that already shows `hasPriority` just before each request, and a pass sent for it is queued and silently consumes the NEXT window (it skipped the player's main phase). `gameCycle` differs between the two, so it is not a usable dedupe key (`priorityRequest` in the game slice).
- Smart mana payment (`game/smartManaPayment.ts`) must enumerate sources from the controlled player's battlefield `rules`, not `canPlayObjects`, and re-solve at every `GAME_PLAY_MANA` because the server asks once per tap. It never uses hidden information (only the own hand, own board and the opponent's visible untapped mana) and bails to manual play instead of guessing (unknown cost tokens, sacrifice or restricted sources, convoke).
- Board FX must stay in the style ratchet: colours come from `ui/tokens.css` (`--mana-*-rgb`, `--ember-rgb`, …) and every decorative animation needs its `html.fx-off` and `prefers-reduced-motion` opt-outs.
- XMage moves a spell onto the stack **before** its targets and costs are chosen, and with auto-payment the whole cast settles within milliseconds of the click, so neither stack entry nor cast completion reads as a separate moment to the player. The heavy-spell slam (`board/gameTransitionEngine.ts`) fires when the spell **resolves**: onto the battlefield, or to the graveyard/exile for instants and sorceries; a countered permanent spell or a cast cancelled back to hand never slams.
- Battlefield bands clip (`overflow: hidden/auto`), so an effect that moves a card across the board must animate a detached clone in a fixed layer (`board/combatStrikes.ts` copies the slot's inherited custom properties and computed transform) and hide the real slot meanwhile.
- The real server usually sends **no** frame for the combat damage steps: a live game against the SIM goes `DECLARE_BLOCKERS` → `END_COMBAT` or straight to `POSTCOMBAT_MAIN` (recorded frames like `attack-pw.json` do show `COMBAT_DAMAGE`, which is what misled the first version of the strikes). Detect combat damage by the transition crossing the damage steps (`crossedDamage` in `board/combatStrikes.ts`), never by `step === 'COMBAT_DAMAGE'`; `e2e/combat-strikes.spec.ts` guards it in real mode.
- A proxy action's ack is sent when the server RMI returns, but server callbacks travel on another socket, so the next prompt can arrive **before** the ack of the answer that caused it. Anything that clears state on ack must check it is still clearing what it answered (`useFeedbackForm` only clears the prompt it sent; clearing unconditionally wiped the new prompt and left the player waiting forever).
- The frame after combat damage already has the dead creatures in the graveyard (SBA ran server-side), and the graveyard top card reuses the same `data-card-id`: DOM lookups for combat must skip off-battlefield slots, and a creature that dies must be cloned *before* React commits that frame (`primeCombatHolds` runs during the presenter render, because child `useLayoutEffect`s run before any parent effect).
- Scryfall's rate limit is per IP, not per tab: the request queue shares its clock and its 429 pause across tabs over a `BroadcastChannel`, and every card lookup must go through the IndexedDB-backed `scryfallJson` (raw `scryfallFetch` means refetching everything on each reload).
- Never guard a fetch effect on "result is still empty" (`releases.length > 0 || loading`): when the fetch fails and returns `[]`, clearing `loading` re-fires it forever (AboutModal news: ~1,400 req/s, froze the desktop app). Use a once-per-mount ref. Every external API the web fetches must also be in the desktop CSP `connect-src` (`launcher/src-tauri/tauri.conf.json`), guarded by `system/desktopCsp.test.ts`.
- A `:hover` must never change the in-flow geometry of what is hovered: a pile that widened its margins on hover re-centred the band (`justify-content: center`), slid out from under a still pointer and flickered collapse/expand forever, shoved the whole row when cards arrived while hovered, and fed its expanded width to `useBandFit`. Piles fan out as an overlay instead (`board/StackPile.tsx`: relative `left` offsets plus an invisible strip that only grows the hover area); guard: `e2e/stack-groups.spec.ts`.
- `GameView.lookedAt`/`revealed` are transient: `GameImpl.fireUpdatePlayersEvent` sends the update and then calls `clearLookedAt()`/`clearRevealed()`, so the prompt that follows a look (Jace, the Mind Sculptor's +2 "Put that card on the bottom?") arrives with them empty. Never close a viewer because the entry left the view: `game/infoWindowState.ts` latches them until the user closes them (desktop `CardInfoWindowDialog` parity) and `GenericDialog` shows them inline while the decision is pending.

## Testing & tooling

- Log checks must be time-windowed from the test start: proxy/server logs are append-only across restarts and old traces cause false positives.
- Real-mode Playwright (`E2E_BACKEND=real`) targets `beta.xmage.today` unless `E2E_SERVER_HOST` is set (`e2e/support/start-game.ts`); when running a spec by hand against the local stack, always pass `E2E_SERVER_HOST=localhost` or it creates tables on the public server.
- Real-mode E2E cannot use scripted fixtures: the server never auto-starts AI-vs-AI tables and advances by priority timers, so the WS helper auto-passes (fake mode is the deterministic loop).
- Keep every generated/imported deck with a concrete printing: the proxy's name-only fallback (`Deck.resolveCardInfo`) is a fork patch, so a real server rejects "17 Forest" with `Card not found`.
- `scripts/gallery-visual.mjs --update` rewrites every baseline in the matrix, not only the ones that changed: after regenerating for one screen, `git checkout` the unrelated PNGs so drift from other work is not baked in.
- Fake-mode specs that inject views through `__mageStore.handleMessage` race the scenario's own frames (the `HumanHelper` acting makes the FakeServer re-broadcast its base view). Views of the same game are ordered by `messageId`, so inject with `messageId: Date.now()`: it is above every FakeServer sequence number, and later scenario frames of that game are dropped as older instead of overwriting the injected view (`game-assist` P/T test failed ~60% under load before).
- `expect.poll` fails immediately when its callback throws (no retry): return a sentinel value for transient DOM gaps instead of throwing.
- `actions/upload-artifact@v4` skips hidden paths by default: uploading `.run/*.log` needs `include-hidden-files: true`, otherwise the integration job silently uploads nothing.
- `scripts/warmup.mjs` must never let an exception escape: an uncaught rejection kills it with only `Node.js vX` as the last line (all `test.mjs` shows); transient stack-not-ready errors are retried for `NEXUS_WARMUP_TRANSIENT_MS` (180 s).
